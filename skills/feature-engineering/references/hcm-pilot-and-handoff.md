# HCM pilot and meeting continuity

Use when preparing a supervised application of the catalog to one real integration request,
reviewing supplied pilot observations, or resuming analysis across customer/provider/engineering
sessions. A prepared protocol is a deliverable; it is not evidence that a real pilot ran. Honor
the user's requested endpoint and existing authorization. This method does not send invitations,
share customer documents or change environments by itself.

## Select a bounded pilot and preserve its starting point

Choose one authorized flow with an accountable analyst, business owner and engineering contact.
Include the provider when its contract or operation changes the decision. Prefer a case with
available questionnaire responses and accessible evidence; do not require a perfect specification
before starting. Confirm the actual domain rather than assuming every checklist is HCM.

Record the starting request, revisions, known answers, existing unresolved items and intended end
of the pilot: meeting preparation, accepted analysis, development readiness or another explicit
endpoint. Keep a dated baseline so later changes can be distinguished from omissions in discovery.
Use only authorized evidence and minimize personal data in samples and shared artifacts.

Preserve two views of the same specification, not independent documents that drift:

- A short customer-facing view: outcome, population, agreed rules, decisions and material questions,
  with named responsible roles and the next action.
- A technical appendix or linked existing artifacts: evidence ledger, contracts, field mapping,
  reconciliation, acceptance trace, limitations and engineering-owned decisions.

Follow the requested deliverable language. Technical detail belongs in the appendix when it does
not help the customer decide. Both views refer to the same revisions and unresolved conditions.

## Run the stages relevant to the endpoint

| Stage                                  | Inputs already available                                                    | Reviewable output and observation                                                                                  |
| -------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Prepare the first meeting              | Questionnaire, attachments, prior decisions and participant roles.          | Reused answers, distinct flows, prioritized consequential gaps; count only questions actually proposed.            |
| Record the discussion                  | Answers and decisions actually supplied, with source/owner.                 | Revised rules, effective dates, exceptions, remaining questions and responsibilities; proposals remain proposals.  |
| Verify technical context               | Applicable product/interface evidence and authorized representative data.   | Evidence coverage, data-quality findings and unsupported capability claims; no deployment inference from a manual. |
| Review with engineering/provider       | Current baseline, alternatives, contract/mapping draft and estimate inputs. | Actual responses, returned gaps and affected criteria; an unanswered request remains pending.                      |
| Resume or close the requested analysis | Baseline plus changed evidence and review observations.                     | Update only affected artifacts, state readiness for the named transition and keep future execution separate.       |

Use the relevant specialist methods rather than repeating every catalog phase. Before claiming a
stage occurred, retain its actual output and observation source. If no participants or environment
are available, finish preparation and mark the pilot execution pending; do not invent meeting
answers or observed benefits to complete the table.

## Resume by changes, not by repeating the interview

Read the last accepted definition, current engineering revision, decision log and open items.
Identify additions, corrections, conflicts and unchanged evidence. For each change, record:

```text
New input / source / time / authority:
Previous statement and revision:
Affected BR/BAC, mapping, contract, criterion, estimate or delivery resource:
Still-valid evidence and independent work:
Decision needed, responsible owner and next observation:
Status of the requested endpoint:
```

A new benefit code may require a map revision and boundary tests; a changed eligibility rule may
also invalidate population and acceptance. A changed provider availability date can affect the
calendar without changing the business rules. Do not reopen settled questions unless the new
evidence makes them relevant. Do not create delivery resources merely to track early meeting
questions; use the existing definition ledger until such resources actually exist.

## Evaluate usefulness using recorded observations

Agree which observations matter before the pilot and retain their denominators and sources:

| Observation                      | Recording rule                                                                                                   | Interpretation limit                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Reopened questions               | Count unique previously answered questions revisited; label new scope, conflicting evidence or missed discovery. | New scope is not automatically a discovery failure.                        |
| Mapping corrections              | Count changed mapping decisions, their reason and affected fields/rules.                                         | A field count alone says little about severity or avoided failure.         |
| Engineering returns              | Count distinct returned issues and whether they block the requested next step.                                   | Multiple comments about one issue are not multiple defects.                |
| Accepted versus pending criteria | Record applicable criteria, their reviewed revision and actual evidence status.                                  | Planned tests and fictional examples do not satisfy executed acceptance.   |
| Time spent, if measured          | Separate preparation, meeting, rework and external waiting using recorded times.                                 | Do not infer time savings from a single run without a comparable baseline. |

Retain disagreements and failed cases; a pilot is useful when it exposes a missing question or an
unsupported recommendation. Compare with a prior workflow only when scope, participants, input
quality and measurement conditions support the comparison. Report differences and confounders;
do not promise a productivity percentage or attribute every improvement to the skills.

Close with artifacts produced, observations actually collected, unresolved issues and concrete
catalog corrections. A well-formed analysis can complete this pilot endpoint while implementation,
homologation and operation remain pending. Use `feature-readiness-review` for the named transition,
and require runtime evidence only where that transition actually needs it.
