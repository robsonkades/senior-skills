# Eight pillars of skill quality

Criteria supplied by the catalog owner. Apply them when creating or substantially updating
skills. Each pillar must appear in the skill's behavior and results; every file does not need
eight repeated headings.

| Pillar            | Definition                                                          | What to look for during review                                                                                              |
| ----------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Precise scope     | When to activate, what to solve and which boundaries to respect.    | The description distinguishes the intended request from neighboring requests; the output stops at the requested endpoint.   |
| Discovery         | Investigate context and clarify questions that change the solution. | Reuses evidence, asks material questions and continues independent work while an answer is pending.                         |
| Technical depth   | Explain mechanisms, contracts, limitations and failure modes.       | Shows how behavior works and fails, with applicability conditions and depth appropriate to the skill's responsibility.      |
| Decision criteria | Compare alternatives, costs and conditions that guide the choice.   | Makes constraints, feasible alternatives, consequences and evidence that would change the recommendation explicit.          |
| Solution quality  | Balance correctness, simplicity, usability and maintainability.     | Solves the problem, is understandable to its audience and avoids complexity or duplication without demonstrated benefit.    |
| Execution         | Turn decisions into concrete actions and reviewable results.        | Produces the requested artifact and records actions, owners or dependencies needed to continue.                             |
| Validation        | Verify results with evidence appropriate to each claim.             | Distinguishes document review, executed testing and pending checks; links results to the revisions and conditions examined. |
| Knowledge limits  | Distinguish facts, assumptions and what still needs verification.   | Does not invent capabilities, rules, approvals or measurements; identifies the gap and required evidence.                   |

## Proportionate application

In a discovery skill, technical depth means recognizing ambiguity in a contract, effective date
or confirmation that changes the business outcome and routing it for validation. It does not
require choosing an architecture. In a contract skill, it requires defining obligations and
failure modes. In a review, execution means producing the requested assessment; it does not
authorize implementing the solution.

A pillar with no new decision in the case may be satisfied by reusing valid evidence and decisions.
Do not manufacture alternatives, tests, meetings or questions to fill the matrix. An unresolved
issue that blocks one choice does not prevent independent work.

## Review before delivery

For each changed skill, record where each pillar is addressed and how it was checked. Review the
body, conditional references, manifest and outputs together. Correct conflicts between them.

Structural validation checks format, packaging, descriptions, references and dependencies.
Critical reading checks written rules. Execution with a realistic case checks observed behavior.
None of these checks alone establishes all pillars in every possible use.

Cases should exercise the ambiguity or failure the skill is intended to resolve. Version
comparisons need comparable inputs and conditions, separating evaluator criteria from agent
materials. Report coverage and limitations without presenting an expected improvement as a
measurement.
